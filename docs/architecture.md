# Voklance architecture

The repository is a React/Vite frontend, an Express API, and a small shared TypeScript package. This is the implementation in the repository; the product brief's Next.js note describes a different setup.

## Frontend

`frontend/src/app` owns providers, routing, and page layouts. `features` owns product-specific pages, components, hooks, API calls, and eventual schemas. `components` holds reusable UI and navigation; `lib` holds the Axios client and TanStack Query configuration; `styles` owns design tokens and responsive CSS. TypeScript aliases map `@/` to `src/`.

The implemented feature directories are `auth`, `onboarding`, `profiles`, `feed`, `communities`, `community-commands`, `referrals`, `events`, `connections`, `messaging`, and `notifications`. `resources` contains a storage-gated metadata foundation. The Home route uses the working chronological text feed; Communities has discovery, membership management, and a structured activity board. The community command picker and forms use the shared Zod payload schemas and existing Axios client.

React Router owns navigation. TanStack Query owns the authenticated user request, onboarding snapshots, catalogs, selections, profile, and history caches. `authApi` calls account endpoints; `onboardingApi` calls the Milestone 3 onboarding and professional-data endpoints through the same credentialed Axios client. The route gate waits for `/auth/me`, then sends guests to `/login`, incomplete accounts to `/onboarding`, and completed accounts to `/app`. Login and signup confirm the newly issued session through `/auth/me` before navigating. Logout and protected API 401 responses remove private query data; account switching also removes the previous account's cache. Network and 503 errors show a retry state without treating the user as signed out. The six-step wizard restores the backend's saved step. Each required step saves its data before advancing; history records have separate CRUD actions. Completion verifies both the completion response and a fresh `/auth/me` result before opening `/app`. Unsaved input stays in component memory after a failed save, and no credential or profile draft is stored in localStorage. Photo upload remains unavailable because there is no approved upload API. CSS tokens define the light palette and a dark palette under `[data-theme="dark"]`. A theme control has not been specified yet.

| Route                      | Guest    | `NOT_STARTED` or `IN_PROGRESS` | `COMPLETED`                                     |
| -------------------------- | -------- | ------------------------------ | ----------------------------------------------- |
| `/`                        | `/login` | `/onboarding`                  | `/app`                                          |
| `/login`, `/signup`        | Allowed  | `/onboarding`                  | `/app`                                          |
| `/onboarding`              | `/login` | Allowed                        | `/app`                                          |
| `/app`, `/app/communities` | `/login` | `/onboarding`                  | Allowed                                         |
| `/account`                 | `/login` | `/onboarding`                  | Legacy redirect to `/app` or `/app/communities` |

Automatic redirects replace browser history entries. A suspended or deactivated account receives a forbidden state with a sign-out control. When verification is enabled, new unverified accounts enter `/verify-email-required`; `/verify-email` remains public for links opened in another browser. On refresh, the browser sends the HttpOnly cookie to `/auth/me`; the seven-day server-side session and current `User` record decide access. A 401 clears account and private query state. A network or 503 failure keeps the user on a retry screen, and a 403 does not turn into a login loop.

## Backend

`backend/src/app.ts` composes middleware and versioned routes. `server.ts` starts the database and HTTP server and closes both on shutdown. `config` validates environment values; `database` manages Mongoose; `common` defines safe error and response helpers; `middleware` handles cross-cutting HTTP concerns. Each implemented module keeps routes, controllers, services, validation, and models separate where needed.

`auth` and `users` retain the existing email/password and session flow. `health` is an implemented API module. Phase 01 Milestone 3 adds protected routes, thin controllers, services, and Zod input schemas under `profiles`, `skills`, `interests`, and `onboarding`. `requireAuth` reuses the existing session service and attaches a typed account identity to each protected request. That service rejects suspended and deactivated accounts with a safe 403; logout remains available. `requireCompletedOnboarding` is mounted on post and community action routes, while onboarding-related APIs remain accessible during setup. The `posts` module implements the professional feed. `communities` and `memberships` implement discovery, membership, and roles. `commands` implements the structured community activity API. The `referrals`, `events`, `connections`, and `messaging` modules implement their respective workflows; `resources` contains metadata and moderation paths while storage-dependent operations remain blocked; the general `notifications` module remains reserved.

Mongoose models use singular model names, explicit field names, timestamps on records that need history, and indexes for established access patterns. Existing live authentication collections are `users` and `sessions`. Additional model definitions now exist for `profiles`, `skills`, `user_skills`, `interests`, `user_interests`, `professional_experiences`, and `educations`; association and experience collection names are explicit in their models. The approved skill and interest catalog seed was run on the local development database during Milestone 4; no user backfill has been run. Only `User` stores onboarding status and current step; completed-step information is derived from saved data. `Profile` has unique `userId` and normalized username indexes. Catalog slugs and user-to-catalog pairs are unique. Experience and education have user/date indexes.

Legacy `User` documents may lack the new fields. Mongoose defaults apply to new documents; auth and onboarding services interpret missing `accountStatus` as `ACTIVE`, missing `onboardingStatus` as `NOT_STARTED`, and missing step as `1`. Existing records are not marked email-verified. New records opt into verification only when its environment switch is enabled; legacy records retain prior access pending an approved rollout. The auth status fallback changes no stored record. An idempotent catalog seed command is available as `npm run seed:catalogs -w backend`; it runs only when invoked. The current local MongoDB was observed as standalone during the audit.

### Onboarding state and ownership

Onboarding, own-profile, catalog, selection, and history endpoints require the existing session cookie. The public profile lookup is the exception and returns only explicitly published profiles for active, completed accounts. Self-service routes derive `userId` from that session. Profile queries use the unique `userId` index; history mutations filter by both record ID and user ID; selections are stored by user ID. DTO mappers return only approved fields. Strict Zod schemas reject extra body fields such as `userId` or MongoDB operators.

`User` is the only persistent onboarding status record. `GET /onboarding` composes a snapshot from the user, profile, catalog selections, and history records. `completedSteps` is derived on the server. `PATCH /onboarding` accepts only a numeric `currentStep`, allows backward navigation, and rejects jumps beyond the next allowed required step. `POST /onboarding/complete` verifies the saved profile, professional status, existing skill and interest references, then conditionally updates one `User` document. Repeating completion leaves the original completion timestamp intact. The existing Profile model requires headline and country on the first save, so these are required for completion even though later product copy calls them optional.

Selection replacement uses a MongoDB transaction on a replica set. On a standalone deployment, the service detects that transactions are unavailable and performs retryable reconciliation: insert desired links first, then remove obsolete links. A failure can temporarily leave extra links, so a replica set is recommended for atomic production updates. The tests exercise both standalone reconciliation and rollback on an in-memory replica set. No transaction is needed for the final onboarding status update because it changes one `User` document.

### Phase 01 migration strategy

1. Deploy the additive fields and new model definitions without changing current auth routes or frontend guards. Existing users and sessions continue to work.
2. New `User` documents receive status and step defaults. Until onboarding services are introduced, code reading legacy documents must use the same effective defaults without assuming that missing values were stored.
3. Do not infer `emailVerifiedAt` for legacy accounts and do not generate usernames from existing names. A future explicit, idempotent backfill may set only missing account/onboarding status fields after its rollout policy is approved; it must never overwrite existing values.
4. Create new indexes before enabling writes to the new collections. Check for duplicate usernames or assignments before any later import. No existing collection is dropped or reset.
5. The onboarding APIs, six-step frontend wizard, and application-wide route gate are enabled. A missing legacy onboarding status enters onboarding under the existing compatibility rule. No backfill or session invalidation is performed.

The `communityactivities` collection stores the initial structured community announcements. Command definitions are a versioned code registry, not a database collection. Referral responses, event registrations, and meetup RSVPs use separate collections. Resource metadata and moderation are modeled, while uploads and downloads remain blocked pending approved storage and scanning. Notifications remain future work.

## API and security conventions

Routes begin with `/api/v1`. Successes use `{ "success": true, "data": ..., "message": "..." }`; failures use `{ "success": false, "error": { "code": "...", "message": "..." } }`. Keep controllers limited to request and response handling, services to business logic, models to persistence, and Zod schemas to input validation. Add future endpoints under a versioned module route and document their request and response contract in `docs/api.md`.

The API uses Helmet, a configured CORS allowlist, a 32 KB JSON body limit, cookie parsing, safe global error responses, request logging without query strings, and an authentication rate limiter. Cookies are HttpOnly and SameSite=Lax, with Secure enabled in production. Production requires a MongoDB URI and HTTPS for cookie-based sign-in. Review rate limits and proxy settings before exposing the API to public traffic.

## Milestone 6 verification architecture

Signup still creates a `User` and MongoDB `Session`. When `EMAIL_VERIFICATION_ENABLED=true`, it sets `emailVerifiedAt: null` and `emailVerificationRequired: true`, creates a 32-byte random URL-safe token, persists only its SHA-256 hash in `EmailVerificationToken`, and asks the SMTP provider to accept a branded HTML/plain-text message. A 24-hour expiry is checked during consumption; the TTL index only removes old records eventually. The token is carried in a URL fragment, removed from the browser address before the POST, and never stored in browser storage. A failed SMTP acceptance deletes the new token, leaves the account/session unverified, and reports failure in the signup response or resend API. Verification atomically deletes the matched token, conditionally stamps the user, then deletes remaining tokens for that user. Concurrent requests cannot both verify successfully.

The switch defaults to `false` and is set to `false` in the local backend `.env`. When off, signup creates no verification token or email, the verification endpoints return `503 EMAIL_VERIFICATION_DISABLED`, and guards allow onboarding. Existing pending accounts are treated as not requiring verification while off; their stored requirement returns when the switch is enabled again. Accounts created while off remain exempt when it is later enabled. Nodemailer SMTP is the single delivery provider behind `EmailProvider`. Local development can use an SMTP mail-capture process on port 1025. Production must configure `APP_PUBLIC_URL`, `EMAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, and optional `SMTP_USER`/`SMTP_PASSWORD`; no credentials are committed. Resend has a MongoDB-backed per-user cooldown and hourly user/IP counters, with defaults in `.env.example`. These counters charge attempts, including failed deliveries, to limit abuse. Auth/current-user, verification, resend, and logout remain accessible to unverified users. Explicit professional-data and onboarding routers use `requireVerifiedEmail` after session authentication. No blanket middleware covers all API routes.

Legacy `User` documents lack `emailVerificationRequired` and may lack `emailVerifiedAt`. They are not labeled verified and retain the old access path. A future legacy rollout could use a grace period or staged enforcement after user communication; no migration or enforcement for those accounts has been run. Approval is required before choosing that production policy.

## Milestone 8 profile management

The existing `Profile`, skill, interest, experience, and education models and owned APIs remain the source of truth. `Profile` adds optional professional links and visibility; no existing document is migrated. New profiles default to `PRIVATE`, and missing visibility on older records is interpreted as private. The public route reads only explicitly published profiles whose owners are active and have completed onboarding. Its DTO excludes email, account and verification state, owner IDs, and unconfigured avatar URLs. Existing skill and history services bound nested reads. Profile edits use Zod allowlists, Mongoose validation, the unique username index, and the current session owner.

Frontend routes `/app/profile`, `/app/profile/edit`, and `/app/professionals/:username` use the existing completion guard and dashboard shell. `features/profiles` owns profile-specific pages, display, hooks, and API composition. The editor reuses the onboarding catalog selector and history forms, and React Query uses the existing onboarding profile, selection, and history cache keys so updates appear in the sidebar and profile page. External links use HTTPS validation and safe new-tab attributes. Image upload is an explicit unavailable state until an approved storage service and upload API exist. No password-reset or GitHub OAuth behavior is part of this milestone.

## Milestone 9 professional feed

`Post` stores author ID, text content, status, and timestamps. `PostLike` and `PostBookmark` have unique user/post indexes; `PostComment` stores flat comments. Feed and saved-post pages use descending `createdAt` plus `_id` cursors, with bounded page sizes. Aggregation filters unavailable authors and posts before the page limit, so older visible results remain reachable. Author records, profiles, counts, and viewer interaction state are batched for each page. A post is visible only while published and its owner is active with completed onboarding. The only supported audience is authenticated professionals; public or other visibility values are rejected. Author usernames are included only when their profile is published.

Post and comment deletes are soft deletes. Deleted post text is cleared, and normal feed, saved-post, like, and comment APIs do not expose deleted posts. Associated likes, bookmarks, and comments remain stored for consistency but are hidden while the post is deleted. Bookmarks are queried only for the session owner. Mutations use session-derived identity, current email-verification policy, completed onboarding, strict Zod allowlists, ownership filters, and a per-user 30-actions-per-15-minutes write limit. The current limiter uses process memory and requires a shared store before scaling to multiple API instances. React Query invalidates the feed, saved posts, and on-demand comments after mutations; no browser storage holds draft or private feed data.

No attachment storage provider is approved or configured. Feed image, PDF, and presentation uploads and downloads are deferred; resource file metadata is modeled separately under the storage gate described below. Community slash commands remain separate from feed comments.

## Milestone 10 professional communities

`Community` stores name, stable unique slug, description, category, tags, owner ID, visibility, status, rules, and timestamps. `CommunityMembership` stores one record per community/user, with a role, status, join timestamp, and history timestamps. A unique pair index prevents duplicate membership; a partial unique index allows only one active `OWNER` membership per community. Community status/category/creation and membership status/creation indexes support cursor pages. Member counts are aggregated from active memberships, avoiding a second counter that could drift.

Discovery and public community summaries can be read without a session. Private summaries hide description, tags, rules, and owner identity from nonmembers, including pending and removed users. Directory and request lists require an active membership with the relevant permission. Role permissions are centralized; the owner can manage all roles, admins can manage moderators and members, moderators may review requests, and members may view the directory. The server derives roles from membership and checks owner identity against `Community.ownerId`; the browser's permission flags only control presentation.

Community creation uses a transaction on a replica set. On standalone MongoDB, a `CREATING` staging record is invisible to all reads until its owner membership exists; write failures trigger cleanup. A process interruption during staging may leave an invisible record for later maintenance. Ownership transfer is available only on replica sets and changes `ownerId`, the old role, and the new role in one transaction. It returns `503 REPLICA_SET_REQUIRED` on standalone MongoDB. The old owner becomes an admin. Community slugs remain stable when names change. An archive is owner-only, read-only under its existing visibility rules, and cannot be reversed through the current API. Members may leave archived communities; owners must transfer ownership before leaving.

Community routes use the existing session, active-account, email-verification, onboarding, origin, and Zod conventions. Writes have a 30-action/15-minute per-user process-memory limiter, which needs a shared store for multiple API instances. React Query holds community pages and invalidates them after mutations; private cache is cleared by the existing sign-out and session-expiry flow. The right sidebar reads `/users/me/communities` rather than static examples. Community images and notifications are future work. No unrestricted community chat is exposed.

## Milestone 11 community commands

The backend registry in `modules/commands/registry` is the authority for command ID, slash name, metadata, enabled state, required permission, payload schema, version, and activity display type. Its original four entries are `/referral`, `/needreferral`, `/event`, and `/meetup`; Milestone 14 adds `/resource` with publication gated by storage. The first four create structured activity snapshots. `@voklance/shared` holds strict Zod schemas and discriminated TypeScript contracts used by the API and forms. They trim text, limit lengths, reject extra fields and markup, validate dates and enums, and permit HTTPS links without credentials. The server checks the registry and schema again before persistence. Slash commands are application actions, not shell commands or ordinary chat messages.

`CommunityActivity` references the existing Community and User models. It stores command type, payload version, validated payload, active/deleted status, and timestamps. Indexes cover community/status/descending creation/ID, the same with command type, and author/descending creation/ID. Deletion clears the payload and hides the record from normal lists. The activity service uses the existing community access resolver and role permission helper: active members may publish; authors or active moderators, admins, and owners may delete. Archived communities reject writes. Private activity requires active membership. Public activity can be read by authenticated, onboarded users. Listing batches visible author and public profile lookups and uses a stable descending cursor with a default page size of 10 and maximum of 50.

The UI under `features/community-commands` gets available commands from the API, filters suggestions as members type, and supports arrow keys, Enter, Escape, and mouse selection. Selection opens a command-specific form; the picker cannot submit raw text. React Query caches command metadata and activity pages, invalidates activity after writes, and the existing logout path clears private cache. Cards render structured fields as React text, with HTTPS external links. The existing 32 KB JSON body limit, session and origin guards, 20-action/15-minute command-write limit, payload allowlist, and server-side ownership checks apply. The rate limiter uses process memory and needs a shared store for multi-instance deployment.

To add a command, define its strict payload schema and types in `shared`, add metadata, permission, and version to the backend registry, then add form fields and a card presentation in the frontend. Keep backend authorization and schema validation authoritative. Attendance check-in, notifications, and messaging remain future workflows.

## Milestone 13 event architecture

`/event` and `/meetup` remain entries in the command registry. The event and activity are created in one MongoDB transaction; the command's optional UUID idempotency key has a partial unique index per community and author. The event stores an `activityId` reference and the activity response includes `eventId`. The generic activity delete route refuses linked event activity, preserving the event/activity relationship. Event editing updates the structured activity snapshot in the same transaction. Cancellation changes the event status; activity DTOs obtain the current event status when rendered.

`ProfessionalEvent` stores community, activity, organizer, type, schedule as UTC instants, original IANA zone, location fields, capacity, confirmed/interested counters, registration availability, and status. Community/status/start/ID and status/start/ID indexes support discovery; organizer/start/ID supports organizer views. `EventRegistration` has a unique event/user index plus user/status and event/status indexes. `MeetupRSVP` has a unique event/user index plus user/response and event/response indexes. Registration and RSVP mutations run in transactions and atomically reserve capacity on the event. Interested RSVPs do not reserve capacity. A standalone MongoDB instance receives `503 TRANSACTIONS_REQUIRED` for these writes. Local development of event workflows therefore needs a single-node replica set or another replica-set deployment. The backend tests use ephemeral MongoDB replica sets and do not touch the development database.

Event list/detail DTOs batch community, membership, organizer, registration, and RSVP lookups. Public communities are discoverable to signed-in, onboarded users; private ones require active membership. Participation requires active membership. Organizer ownership or active owner/admin role permits edit, cancel, and attendee viewing. The attendee endpoint is privacy restricted; meeting links appear only for managers or confirmed participants while scheduled. Activity URLs are always redacted. Text is stored as text and rendered by React as text. The frontend uses the existing Axios client, router guards, and React Query cache; event mutations invalidate event and community views, while sign-out clears private caches. The form resolves wall-clock values in an explicit IANA zone and rejects daylight-saving gaps or duplicate times. The backend validates the supplied offset against that zone.

The UI routes are `/app/events/:eventId` and `/app/events/:eventId/edit`; community detail shows upcoming event cards and linked activity cards. The standalone events listing page has been removed. Paid tickets, payment, calendar synchronization, conferencing, notifications, check-in, and general community messaging are outside this milestone.

## Milestone 14 resource foundation and storage gate

The command registry includes `/resource` with the existing active-member permission. Its shared payload schema and `CommunityActivity` validation are in place. The command service rejects valid resource publication with `503 RESOURCE_STORAGE_UNAVAILABLE` before creating an activity, because the repository has no approved object storage or malware scanner. This is an intentional product gate, not an upload stub that silently stores files. The resource form allows local selection for immediate extension/MIME/size feedback but clearly says nothing is uploaded or saved. Backend upload routes do not accept a file. No large document is stored in MongoDB or a public directory.

`StoredFile` models metadata only: uploader, provider identifier, private key, original and safe filenames, MIME, size, checksum, scan status, and lifecycle status. The storage key and original filename are excluded from ordinary queries. It has unique-key and uploader/status/time indexes. `CommunityResource` references a community, activity, creator, and one stored file; its activity and file references are unique. Community/status/time, creator/time, category, tag, and text indexes support discovery. `ResourceReport` stores reporter, reason, review state, and reviewer audit fields, with unique resource/reporter and community/status/time indexes. These models are ready for an approved storage integration; the application provides no path to create a clean file or publish a resource until that dependency is resolved.

Read APIs, metadata editing, soft deletion, reporting, and moderation work for canonical records. Reads batch community, membership, author, and safe file metadata lookups and use cursor pagination. Public community metadata is visible to signed-in users; private metadata requires active membership. Downloads additionally require active membership and a published resource with a clean attached file. They return 503 after those checks because storage is absent. Hidden or deleted resources are inaccessible to ordinary viewers and excluded from listings and activity cards. Owner or active owner/admin/moderator may edit or delete; moderators may hide resources or dismiss reports. Reports omit reporter identity from the API. Metadata edits, deletion, and moderation changes use replica-set transactions to keep resource and activity states aligned. Deleted file metadata is retained for audit; physical cleanup requires a future private storage lifecycle policy.

Frontend routes are `/app/resources/:resourceId` and `/app/communities/:slug/resources`, using the existing router guards, Axios client, React Query, and private-cache clearing behavior. The standalone My resources page has been removed. Community resource search, categories, tags, status, empty/loading/error states, and moderation review are wired to the backend. Preview and download controls are visibly unavailable while the storage gate is closed. Office previews will require an approved isolated conversion service; untrusted Office documents are never embedded in the app. PDF preview and download remain blocked until private storage, scanning, and authorized delivery are available. Feed attachments remain separate and unavailable.

## Milestone 15 professional connections

`Connection` stores one canonical pair with `userLowId` and `userHighId` sorted by ID, plus requester, recipient, status, request/response times, and timestamps. A unique pair index prevents duplicate requests in either direction, including concurrent sends. Recipient/status/time and requester/status/time indexes serve pending lists; pair-side/status/ID indexes serve accepted lists and counts. The service performs conditional atomic status changes. A declined, cancelled, or removed pair can be requested again only after the configurable cooldown. This single-document workflow works on standalone MongoDB and a replica set; no community membership write occurs.

Discovery uses the existing `Profile`, `User`, `UserSkill`, and `Skill` models. It filters explicitly published, discoverable profiles belonging to active completed users before limiting a page. Name/headline and city/country substring filters are escaped, and skill filtering uses the catalog relationship. Pages and profile summaries batch lookups to avoid one query per card. The profile visibility and network settings are checked on the server for requests and shared lists. Existing published profiles remain discoverable by default; unpublished and legacy profiles remain private. Connection list sharing defaults to private and, when enabled, is limited to accepted connections; unpublished or unavailable contacts remain hidden. Accepted counts are derived from relationship records and are not stored as counters. Search is bounded but regex matching may need a dedicated search index as the profile catalog grows.

The frontend uses the existing protected app layout, Axios client, and React Query. `/app/network` has accepted, incoming, sent, and privacy views; `/app/network/discover` has server-backed filters and cursor loading. Public profile buttons query username-relative status without changing the existing public profile DTO. Mutations invalidate network caches, and the existing sign-out flow clears them. Per-user request limits and a cooldown reduce repeated unsolicited requests; the limiter follows the project's current process-memory pattern and needs a shared store for multi-instance deployment. No private messaging, notifications, contact import, or community chat was added.

## Milestone 16 direct messaging architecture

The existing Express HTTP server hosts Socket.IO at `/socket.io`. Handshakes accept only configured origins and authenticate the existing MongoDB session token from the HttpOnly cookie through `getCurrentUser`; there is no second login scheme. Session validity is rechecked on each event and every 60 seconds, and logout disconnects sockets for that session. The browser uses the same-origin Socket.IO client and does not read the cookie. The Vite development proxy forwards `/socket.io` WebSocket upgrades to the API.

`Conversation` stores one sorted pair with a unique compound index, last message reference, and activity timestamp. `Message` stores plain text and a unique `(senderId, clientMessageId)` pair for retry safety; `(conversationId, _id)` serves cursor history. `ConversationParticipantState` has one record per user and conversation for independent read position, mute, and archive settings. `UserBlock` has a unique directional pair. `MessageReport` stores a private reason and review status, unique per message and reporter. `Profile` holds direct-message, read-receipt, and online-visibility choices. No migration is required: missing profile settings use the documented defaults.

REST and Socket.IO call the same conversation and message services. Every protected operation checks pair membership, both account states, accepted connection, both messaging preferences, and two-way block status. Inboxes filter inaccessible pairs before pagination. A connection removal, block, or messaging opt-out emits access revocation and evicts joined conversation rooms. Message persistence precedes broadcast. The sender supplies a UUID; duplicate delivery returns the saved message, and the React Query cache reconciles by message ID or client UUID. The UI retries a failed optimistic message with the same UUID. Reconnect invalidates server-backed inbox/history/unread queries. Read position advances atomically and only against received messages; the sender sees a receipt only when the reader opts in. Presence subscriptions require an eligible connection and the target's visibility setting; the last socket leaving marks the user offline. Typing state is throttled and expires automatically.

The inbox at `/app/messages` has search, per-thread history and cursor loading, unread badges, mute/archive/block/report controls, settings, and mobile navigation. Published profiles and My Network expose a Message action only for accepted connections. Message notification events produce a short in-app notice, suppressed for muted threads or the currently viewed conversation. Community command activities use their existing models and routes; they do not enter direct-message conversations.

The current Socket.IO adapter, presence map, typing timers, and socket limits are process-local. Multi-instance deployment needs a shared Socket.IO adapter, distributed presence and rate-limit state, and a cross-instance event publisher before routing live sockets across nodes. Delivery is real-time while clients are connected; MongoDB history and unread queries recover after reconnect. There is no push/email delivery, attachment support, end-to-end encryption, or moderation review interface for message reports in this milestone. Report documents remain private to server-side operational review.

## Milestone 17 notification architecture

`Notification` stores controlled type/category, recipient, optional actor, structured entity target, safe text, read timestamp, and a recipient-scoped unique deduplication key. Recipient/time, recipient/category/time, and recipient/read indexes serve list and count APIs. `NotificationPreference` has a unique user/category index and enabled defaults. Feature services enqueue `NotificationOutboxEvent` records after successful operations; the outbox uses a unique recipient/key pair, immediate processing, a 15-second retry worker, bounded backoff, and a processing lease so an interrupted worker can recover. `Notification` remains the source of truth for offline delivery and read state. Socket.IO only publishes safe DTOs to authenticated recipient rooms; the frontend invalidates React Query data on reconnect and renders text as text.

Connection, post, referral, community, event, meetup, and message producers use deterministic keys. The resource producer is dormant because resource publication is blocked pending storage and scanning. Notification creation follows business writes in workflows that already support standalone MongoDB; those origin writes and outbox inserts are not one atomic transaction. A process or database failure in that narrow interval can leave an event without a notification. Existing event transactions keep their own business invariants, but the post-commit notification enqueue has the same limitation. Multi-instance delivery also needs the shared Socket.IO adapter described above. No email, SMS, mobile push, or browser push channel is implemented.

## Milestone 18 GitHub integration

`GitHubOAuthState` stores a hashed random state, Voklance session hash, PKCE verifier, and 10-minute expiry. The callback consumes that record once, exchanges the code server-side, verifies `/user`, and revokes the OAuth grant before saving a `GitHubConnection`. Only a stable GitHub numeric ID, username, and allowlisted public URLs are persisted. Repositories are fetched without a token from the public API; only repositories owned by that GitHub ID and marked public are cached in `GitHubRepository`. Each repository is unique per Voklance user and GitHub repository ID. Manual sync locks a connection, applies a cooldown, and marks absent repositories unavailable only when all public pages were retrieved. A partial run is labelled partial. Public portfolio reads require a published profile and active completed account and return featured, available repositories only. Disconnect removes the connection and cached rows. Rate limits on unauthenticated GitHub API requests can defer sync; there is no background sync or GitHub webhook in this milestone.

## Milestone 19 unified search

The search module uses each collection's MongoDB text index to retrieve a maximum of 250 candidate records per category. It filters those candidates against active users, published and discoverable profiles, reciprocal blocks, active community membership for private communities, active events and referrals, published resources, and connected public GitHub repositories. Results are normalized to shared DTOs before deterministic ranking. Exact title/name matches score 100, prefixes 80, title contains 60, description contains 30, and other text-index matches 10; recent sorting uses creation time then ID. The All tab returns independently bounded category previews, while category pages use a bounded offset cursor. The 250-candidate cap limits broad or common queries, and results can be incomplete above that window. Search does not scan document bodies, private conversations, or referral applications. Text indexes require MongoDB index creation on deployment; Atlas Search and external search services are not assumed. The suggestions endpoint reuses the same privacy checks and a per-process rate limit.

## Milestone 20 rule-based recommendations

`recommendationContextService` reads the current user's selected onboarding interests, assigned skills, optional feed topic preferences, accepted connections, active community memberships, and reciprocal blocks. It does not inspect private messages or referral applications. The For You feed retrieves at most 250 recent post candidates and filters blocked, inactive, unpublished, deleted, and feedback-suppressed records before ranking. A topic substring match adds 30 points; an accepted author connection adds 20; freshness adds `round(10 / (1 + ageDays / 7))`, using the cursor's `asOf` timestamp. Ties sort by creation time and ID. A deterministic pass avoids a third consecutive post by the same author when another candidate exists. Following and Recent use chronological order. The cursor fixes scoring time, but content edits and feedback changes can still shift later pages; the bounded candidate pool can omit older posts.

Category suggestions examine at most 120 recent candidates each, enforce the same public and community visibility boundaries as search, exclude existing or pending connections from people suggestions, exclude joined communities, and hide dismissed records. Topic and joined-community matches produce controlled reasons and scores. Feedback is unique per user, entity, and action and can be undone. Topic preferences supplement existing onboarding selections rather than copying or overwriting them. This is deterministic relevance guidance, not a measure of professional quality or hiring suitability. Per-process rate limiting bounds refreshes; distributed deployments need a shared rate-limit store.

## Milestone 22 account security and privacy

The existing user and session models now carry a `sessionVersion`. A session created before this change has effective version zero; a password reset/change, confirmed email change, logout-all, or deactivation increments the user version, invalidating every older cookie even if physical session cleanup fails. Session records include coarse browser/device text, creation and expiry times, and last-seen time updated at most every 15 minutes; no IP address or device fingerprint is stored. Session list DTOs omit token hashes. Socket connections are disconnected on security changes and still recheck the session during events. Logout-others retains only the current token hash.

Password recovery and email change use random 32-byte opaque tokens, SHA-256 hashes at rest, 30-minute expiry, TTL cleanup, and atomic `findOneAndDelete` consumption. New requests replace old tokens. Passwords use the existing scrypt service. A configured SMTP host, sender, and public frontend URL are required outside tests; provider failures delete unsent tokens. The forgot-password API uses one generic success message for known and unknown email addresses. Email change verifies the current password and leaves the old address active until a signed-in member confirms the new address. Confirmation uses MongoDB's unique email index to resolve races and invalidates all sessions. Deactivation retains data and privacy settings, hides the account through existing active-user checks, and requires the password plus explicit UI confirmation; `/auth/reactivate` verifies the password before restoring active status. There is no second authentication system.

Data export is assembled in memory after password verification and returned directly with no temporary file. It has a 1000-row limit for each authored-data collection and a 5 MiB serialized limit, rejecting oversized exports rather than silently truncating. Security audit events record only the user ID, action, and time, expire after one year, and are best effort because writes are not transactionally coupled to the originating action. They are not exposed through ordinary APIs.

Permanent account deletion remains gated with `503 ACCOUNT_DELETION_UNAVAILABLE`. The current inventory needs a durable, retryable cleanup policy before acceptance: account, profile, sessions and reset tokens must be deleted; user-owned credentials and GitHub snapshots removed; memberships and connections removed; notification, bookmark, preference, and feedback records removed; authored posts, comments, activities, referrals, events, resources, and direct messages need a documented delete or anonymize policy that preserves other users' shared context and community ownership invariants. Existing resource publication is storage-gated, but future uploaded files would require external object cleanup. The notification outbox is not a general deletion worker. No request is accepted or account disabled for a deletion operation that cannot finish safely.

## Milestones 23, 25, and 26

The responsive shell uses one navigation tree across screen sizes. At narrow widths, the drawer is toggled from the top bar; Escape, navigation, and viewport expansion close it. The same links and access gate apply at every size. The skip link, visible keyboard focus, and reduced-motion rule are global.

`Bookmark` is the canonical user/type/target save with a unique compound index. On first unified-bookmark use, legacy `PostBookmark` records are upserted with their original date and removed; retrying migration is safe. `BookmarkCollection` has a unique case-insensitive name key per user, and `BookmarkCollectionItem` has a unique collection/bookmark pair. Each mutation scopes IDs to the current user. Saved-item hydration batches target, author, block, community, and membership lookups and replaces revoked targets with generic unavailable entries. Search and sorting currently operate within 250 recent bookmark candidates. Personal activity is derived from canonical collections rather than stored in another log; its retention equals the source record's retention. Deleted source records disappear, and account deletion remains gated as above.

`ProfileCertification` and `ProfileProject` are owned by the same user as the canonical `Profile`. Public profile reads enforce published profile and active-account checks before fetching either. URLs are validated as HTTPS without embedded credentials at the API boundary; project repository links are user claims, while the GitHub repository showcase is sourced from the verified GitHub account's public API snapshot. Featured projects have an application-level maximum of four. Profile completeness is deterministic from current profile sections and available only to the owner. Section order is stored on the profile and validated as a complete permutation. Visitor pages call the public profile API and receive no private owner editing data.
People search uses project and certification text indexes to find candidate owners, then applies the same published, discoverable, active-account, and block filters used for other people results. People recommendations may match explicit member topics against public project text but do not claim skill verification or use the completeness score.
`ProfileUsernameAlias` reserves prior usernames and resolves old public profile links to the current profile. Alias resolution still applies the current visibility and active-account checks; old usernames cannot be claimed by a different account. A future durable account deletion workflow must remove aliases, certifications, projects, saved items, and collection memberships along with the earlier data inventory.
